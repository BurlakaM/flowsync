# FlowSync — продуктивність: вимірювання, знахідки, виправлення

Ціль із `docs/SLO.md`: p95 часу відповіді API **< 300 мс**. Цей документ показує, як це міряємо, що знайшли й що виправили,
з цифрами «до» і «після». Перезапуск: `./ops/load/run.sh`.

## Як міряємо

| | |
|---|---|
| Інструмент | k6 (контейнер `grafana/k6`), сценарій `ops/load/scenario.js` |
| Об'єкт | **прод-образ** backend (`NODE_ENV=production`), окрема БД `flowsync_perf` у dev-Postgres; ліміт частоти піднято лише для цього інстансу (`RATE_LIMIT_PER_MINUTE`) |
| Дані | `ops/load/seed.sql`: 50 користувачів, 40 проєктів, **60 000 задач**, **180 000 коментарів**, 100 000 записів активності, теги й виконавці |
| Навантаження | 20 віртуальних користувачів: розгін 20 с, тримання 60 с, спад 10 с |
| Суміш запитів | 15 % список проєктів · 25 % задачі проєкту з фільтром · 15 % пошук · 15 % картка задачі · 10 % коментарі · 8 % активність · 7 % новий коментар · 5 % зміна статусу |
| Машина | Windows, Docker Desktop, 8 CPU, 8 ГБ; **усе на одній машині** (backend, Postgres, k6, решта dev-стека) |

Абсолютні цифри залежать від машини, тому порівнюємо лише прогони на одній машині. Різниця «до/після» нижче — один і той самий
сценарій, ті самі дані. Між прогонами є шум (інші контейнери, кеші), тож дрібні відмінності (десятки відсотків) нічого не доводять,
а триразові — доводять.

## Знахідка 1: лічильник коментарів і задач читав ВСЮ таблицю (головна)

**Симптом.** Навіть найпростіші читання (картка задачі, список проєктів) мали сотні мілісекунд p95, а процесор БД був завантажений.

**Як знайшли.** Увімкнули `log_statement = 'all'` для тестової БД, подивилися SQL, який генерує Prisma для списку задач, і запустили
`EXPLAIN (ANALYZE, BUFFERS)`. `_count: { select: { comments: true } }` Prisma перекладає як

```sql
LEFT JOIN (SELECT task_id, COUNT(*) FROM comments GROUP BY task_id) a ON tasks.id = a.task_id
```

і для списку з 20 задач планувальник робить:

```
->  HashAggregate (actual rows=60000)            -- групування по ВСІХ задачах
      ->  Seq Scan on comments c (actual rows=180198)   -- читає всі 180 000 коментарів
Execution Time: 54.652 ms                        -- із них ~45 мс на цей підзапит
```

Тобто вартість не залежить від розміру сторінки: 20 задач чи 1 — завжди повне сканування. Те саме для `_count: { tasks }` у проєктах.
Для однієї задачі за id планувальник «проштовхує» умову й усе добре (0,125 мс), тому в тестах на малих даних проблеми не видно.

**Виправлення.** Лічильники рахуємо окремим запитом лише для id зі сторінки (`groupBy` + `where taskId in (...)`), його обслуговує
індекс `comments(task_id, id)` без читання коментарів: 0,05 мс. Один зайвий запит на сторінку замість повного сканування на кожну.
Код: `TasksService.withCommentCounts`, `ProjectsService.taskCounts`.

**Ефект.** Пропускна здатність ×3, p95 «задач проєкту» 886 → 246 мс, «списку проєктів» 302 → 146 мс. Навіть запити, яких це
не торкалось (активність, коментарі), прискорились у 2,5–3 рази, бо БД перестала сканувати таблиці на кожен запит.

## Знахідка 2: пошук не користувався індексом задач

`EXPLAIN` показав `Seq Scan on tasks` (60 000 рядків) і повторний `to_tsvector` на кожному рядку, хоча GIN-індекс
`tasks_fts_idx` існує. Причина: умова «збіг у задачі **OR** є коментар зі збігом» — планувальник не може використати індекс задач
для гілки з `OR EXISTS`.

**Виправлення.** Дві окремі гілки через `UNION` (кожна має свій GIN-індекс: `tasks_fts_idx`, `comments_fts_idx`), потім ранжування:

```
Було:  Seq Scan on tasks → Filter (OR EXISTS ...)      Execution Time: 743.6 ms
Стало: BitmapOr двох Bitmap Index Scan → HashAggregate  Execution Time: 179.9 ms   (4× швидше, без зміни схеми)
```

**Побічне виправлення коректності.** Раніше пошук брав 1000 найкращих збігів **з усієї БД**, а доступ до проєктів перевіряв потім.
У великій базі чужі задачі витісняли б видимі з топ-1000. Тепер `rankedIds` отримує список доступних проєктів
(`ProjectsService.accessibleIds`, те саме правило доступу, що й скрізь) і обмежує пошук ними.

## Знахідка 3: N+1 немає (перевірено)

Кількість SQL-запитів на один HTTP-запит (журнал Postgres, `log_statement = 'all'`):

| Запит | SQL-запитів |
|---|---:|
| список проєктів | 2 |
| задачі проєкту (20 шт., зі виконавцями, тегами, лічильниками) | 2 |
| пошук | 3 |
| картка задачі | 2 |
| коментарі | 2 |
| активність | 2 |
| новий коментар (транзакція, outbox, аудит, сповіщення) | 7 + 2 транзакції |

Кількість не росте з розміром сторінки: виконавці й теги вантажаться одним `IN (...)` на всю сторінку.

## Що лишилось (чесно)

- **Пошук p95 871 мс** > 300 мс. Решту часу з'їдає ранжування `ts_rank`, яке перераховує `to_tsvector` для ~18 000 збігів. Кандидат:
  збережена згенерована колонка `tsvector` + GIN-індекс по ній (потребує міграції з `Unsupported("tsvector")` і перевірки дрейфу схеми;
  виграш **не міряли**). Синтетичні дані тут суворіші за реальні: кожне з 20 слів трапляється у ~10 % задач.
- **Запис (новий коментар 515 мс, статус 400 мс).** Кожен запис — це кілька окремих комітів: транзакція зміни з подією, claim події,
  запис аудиту, позначка «доставлено». Кандидат: об'єднати доставку в одну транзакцію або віддавати доставку relay-ю. Не робили:
  це змінює гарантії фази 12.
- Прогін на ноутбуці з усім стеком на одній машині; на окремому сервері цифри будуть іншими. Вимірювати треба на тому, що буде в проді.
